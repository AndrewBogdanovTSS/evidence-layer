Checks that turn a review's assertions into claims that could be proved wrong.

A review - written by a person, or generated by a model that just wrote the
change it is reviewing - can assert anything at all about what it read and what
it ran, in prose that reads identically whether or not any of it happened. A
README asserts a test count, a build size, a set of pinned versions; all true
when written, none of them with a clock. This package closes that gap for an
ordinary project: one executable whose commands each take one kind of claim
and make it falsifiable, plus a journal that gives the whole layer a clock. It
runs on Node; the project it checks need not - test counts are read from JUnit
XML, pytest, vitest and Node's own runner.

**Falsifiable** does not mean fragile or fakeable. It means testable: you can
name, in advance, what would prove the claim wrong. A claim that survives every
possible observation is not strong, it is empty.

## Install

```bash
npm install --save-dev evidence-layer
```

Requires Node 22 or newer. Zero runtime dependencies.

Node 20 is not supported, and the reason is a date rather than a taste:
it reached end of life on 2026-04-30 and receives no security patches.
A package whose entire subject is claims with a clock does not get to
quietly support a runtime that stopped having one.

## AI-driven development, and the vibe-coding case

A coding agent writes the change and then writes the account of the change. Both
come out of the same model, in the same fluent prose, and the account reads the
same whether the suite ran or not. "I ran the tests and they pass" is a
plausible next sentence, which is all a language model needs in order to emit
it. Plausibility is not observation, and nothing in the surrounding text tells
you which one you got.

That is not an accusation of lying. It is cheaper than lying: gathering evidence
is off the trajectory the writer is already on, and a sentence costs nothing.
The identical failure occurs in human reviews - it is only that nobody could
previously generate a thousand of them a week.

Vibe coding sharpens the problem to a point. The whole trade is accepting code
you did not read, which leaves the model's summary as the only thing standing
between you and the diff. An unchecked summary is not a compressed version of
reading the code; it is a different artifact that happens to be made of the same
words.

What this layer changes, concretely:

- **Gathering moves off the writer.** `gatherEvidence()` runs the expensive
  commands *before* the review is written, with something that is not the
  reviewer, and writes the results into `evidence.local.md` as artifact blocks a
  review can cite. It refuses to run when the working tree is not at the commit
  you asked about - an agent that drifted a commit mid-session otherwise
  produces confident evidence about a different codebase.
- **Every claim carries an address.** `VERIFIED[tests-a3f91c]` names the exact
  artifact it rests on, and `claims` resolves that id, checks it was collected
  at the commit under review, and warns when one artifact is quietly backing
  four unrelated claims. A bare tag any writer can satisfy for free carries no
  information; an id is either in the document, at that commit, or it is not.
- **The receipt proves the agent read *this* repository.** Stale context
  windows, files renamed three commits ago, paths reconstructed from a
  half-remembered tree: `receipt` checks the review's Access Receipt against
  git's own output, and backs every cited file with that file's verbatim first
  line. The baseline is checked by equality against
  `merge-base origin/<target> <head>`, never ancestry, because a stale base
  fails in the reassuring direction - the diff comes out *larger*, so nothing
  looks missing.
- **Honest stays cheap, which is the only reason any of it gets used.**
  Gathering writes a skeleton with the ids already substituted, so citing an
  artifact means *leaving a block in place*, and asserting something unbacked
  means *deleting part of the template*. A convention that costs the writer more
  than the shortcut loses to the shortcut every time, model or not. A run its
  time limit killed is suggested as "did not complete", never as a failure it
  never got to report.
- **A wrong citation comes back with its correction.** A writer that cites
  the wrong block or the wrong number - the mistake a smaller model makes most -
  is not left to work out the fix from a sentence. Every failing finding
  carries one, read off the run rather than guessed: the claim the cited run
  does back, as the skeleton would write it, with its predicates filled in.
  `claims review.md --fix` applies the one fix that needs no judgement, marking
  every failing claim UNVERIFIED, so the cheapest way past a finding says less,
  never more. Nothing here needs the writer to be a strong model; it needs it
  to copy two lines.
- **Agent review gets a scorecard instead of a vibe.** A commit fixing a bug a
  review let through adds `Missed-By: <review or PR>` to its own message, and
  `governance` extracts those into the journal on every run. "Is the agent's
  review catching anything real?" becomes a count over time - a floor, never a
  rate ([`src/core/misses.ts`](src/core/misses.ts) says why).
- **The output is machine-readable, so the loop can close.** Exit codes are a
  contract, every check reports the same five levels, every finding carries a
  stable reason code, and `--format json` prints the whole report as one
  document. An agent can run the check, read its own grade, and fix the finding
  before a human opens the PR - and with the runtime gate, it has to, because
  the check runs when it tries to stop.
- **Artifact ids do not depend on your terminal.** Captured output is
  ANSI-stripped before it is hashed, because `FORCE_COLOR` is set in most CI
  environments and inherited by every child process. An id that changes with the
  terminal is not an address.

What it does not do is judge whether an artifact's output actually *supports*
the sentence next to it. That needs reading output for meaning - a probabilistic
judgement, and putting one inside a deterministic checker reintroduces exactly
the circular validation this layer exists to avoid. See [what this does not
do](#what-this-does-not-do) below, and
[`examples/plain-node-project/reviews/shotgun-artifact.md`](examples/plain-node-project/reviews/shotgun-artifact.md)
for the fixture that passes on purpose to prove the limit is real.

## The one rule everything here is graded against

**The honest path must be cheaper than the convenient one** - fewer tokens,
fewer separate decisions, less distance from the trajectory the author (human or
model) is already on. Nothing here relies on anyone wanting to be careful.
Anything that made correctness more expensive than a shortcut was rejected or
rebuilt before shipping - see `src/core/skeleton.ts`'s file header for the one
concrete near-miss.

## The commands

One executable, seven commands - `journal` is the one command with
subcommands, and `hook` and `init` are the runtime gate's (see
[below](#in-an-agents-session-the-runtime-gate)):

```bash
npx evidence-layer claims review.md          # is every claim backed by evidence?
npx evidence-layer receipt review.md         # was this review written against this repo?
npx evidence-layer ci-summary output.txt     # render captured output as a CI summary
npx evidence-layer governance                # is anything actually running the checks?
npx evidence-layer journal report            # what the checks have actually found
npx evidence-layer journal tag <id> real     # mark a finding real or false
```

| command | the claim it makes falsifiable |
| --- | --- |
| `claims` | "I verified this" - every `VERIFIED[id]` tag must address a real artifact collected at the commit under review; with `--seal`, one this checkout's gather wrote about this code, and with `--bundle`, one a given bundle carries |
| `receipt` | "I read this repository" - the review's Access Receipt must match the repository's own git output, and a cited file must be backed by that file's own verbatim first line |
| `ci-summary` | nothing; it renders a captured run for a CI job summary, and reports `unverifiable` when it has nothing to read |
| `governance` | "this is enforced" - every invariant a decision record declares must be reachable from a git hook or a CI workflow, and no governance exception may be past its expiry; on the way, it records every `Missed-By:` commit trailer into the journal (`--no-journal` to skip) |
| `journal report` | "these checks are useful" - real findings, false findings and misses, counted over time rather than assumed |
| `journal tag` | as above, at the moment of fixing, by whoever fixed it |
| `hook` | the runtime gate, as Claude Code or Codex runs it - see [below](#in-an-agents-session-the-runtime-gate) |
| `init claude`, `init codex` | nothing; it writes the gate's hooks into the project's agent configuration |

`claims`, `receipt` and `governance` print text by default, `--format json`
for a program, `--format github` for a GitHub Actions step and `--format azure`
for an Azure Pipelines step - see [Exit codes are a
contract](#exit-codes-are-a-contract).

A receipt quotes each cited file in a table - one row per file, the first
non-blank line in a code span, `|` escaped as `\|`:

```markdown
**Sample integrity**:

| File | First non-blank line |
|---|---|
| `src/a.ts` | `import { b } from './b'` |
```

The one-line form from 0.1.x (`` **Sample integrity**: `path` -> `line` ``) is
still read, so existing reviews keep verifying.

The colon-separated names these checks had before they were a package
(`check:claims`, `check:receipt`, `ci:summary`, `journal:report`,
`journal:tag`) still work as aliases.

Gathering is deliberately **not** a subcommand. It runs whatever your project's
own commands are, at your project's own gates and timeouts, so it is a library
call in a script you own rather than a CLI flag pretending to know them.

## The loop, in a project with an agent in it

```js
// scripts/evidence.mjs - run before the review is written, not after
import { gatherEvidence } from 'evidence-layer'
import { summariseNodeTest } from 'evidence-layer/adapters/test-reports'

await gatherEvidence({
  repo: process.cwd(),
  base: 'origin/main',
  summaries: { test: summariseNodeTest() }, // how much the test step checked
})
```

[`examples/plain-node-project/scripts/evidence.mjs`](examples/plain-node-project/scripts/evidence.mjs)
is the full version for a project on `npm` and `node --test`, and
[`test/example.test.ts`](test/example.test.ts) runs the whole loop below on it.

```bash
node scripts/evidence.mjs               # artifacts + a pre-filled claim skeleton
npx evidence-layer claims review.md --seal  # does every VERIFIED[id] resolve, to this run, about this code?
npx evidence-layer receipt review.md    # was this written against this checkout?
npx evidence-layer governance           # and is anything actually running the above?
```

Step one carries the weight, and it is the step an agent will skip on its own,
because it is off the path. Put it in the script the agent is told to run, not
in the instructions it is told to follow.

The last step belongs in CI rather than on the machine that wrote the change -
[the GitHub Action](#in-ci-the-github-action) is one step. Every check here can
be run by whoever wrote the diff, which makes a passing local run a
self-report - and anyone who skipped the gathering step skips the verifying
step just as easily. Same commands, different party - and for the evidence to
be the other party's too, the gathering goes in CI as well, ahead of the review
([below](#in-ci-the-github-action)). Between the two, the
[runtime gate](#in-an-agents-session-the-runtime-gate) runs them when the agent
says it is done.

## Exit 0 is not the same as "it passed"

`claims` reads the outcome of every artifact a VERIFIED claim cites, and three
rules are mechanical enough to check without reading the output for sense:

- **A failing run backs no success claim.** "Tests pass" over `exit: 1` is an
  error.
- **A stopped run backs only "did not complete".** The exit line names why it
  stopped (`exit: 124 (timeout)`, `exit: 1 (overflow)`, `exit: 137 (killed
  SIGKILL)`), so "Typecheck reports errors" over a run the time limit killed is
  an error too: that run reported nothing at all.
- **A run that checked nothing backs no success claim.** A linter whose every
  file was ignored and a test run whose every test was skipped both exit 0. The
  gatherer ends lint and test output with one work-summary line, e.g.
  `[SUMMARY tests: passed=71 failed=0 skipped=0 todo=0]`, when it is given a
  summariser for that step (below); a success claim over a summary showing zero
  work, or any errors, warnings or failures, is an error.
  `lintClaims(md, file, { requireWorkSummary: true })` also rejects a success
  claim over a lint or test artifact that carries no summary.

Two more rules hold the claim's own words to the block it cites, just as
mechanically:

- **A claim cites a run of the kind it names.** "Lint reports no violations"
  over a typecheck block is the wrong block - `claims/kind-mismatch` - whatever
  that typecheck showed. The kinds are `classifyCommand`'s: tests, lint,
  typecheck, lockfile, audit ("dependency audit", not a bare "audit" or
  "vulnerability", which are ordinary words in a security fix's claims). A
  claim that names none, or names several including the run's, is held to
  nothing.
- **A count the claim states is the run's count.** "72 passing tests" over a
  work summary of `passed=71` is `claims/count-mismatch`, predicate or no
  predicate. A number is read only where a word ties it to the run - "71
  passing tests", "ran 71 tests", "7 files were linted", "3 skipped" - so
  "adds 3 tests" and "touches 12 files" are left alone, and so is a sentence
  about what used to be true ("fixes the 2 failing tests"). Nor is the number
  a count is taken out of: "3 of 71 tests failed" is not read as 71 failures.
  A number spelled out, zero to twenty, is the same number: "four passing
  tests" over `passed=3` fails like "4 passing tests" does. "Ran N tests" may
  be the passed count or the total; a count of a kind the run does not
  summarise is left alone.

Each of these rules has a fixture that fails it on purpose, over real runs of
the example project's suite -
[`outcome-mismatch.md`](examples/plain-node-project/reviews/outcome-mismatch.md)
(a failing run, a timed-out one, one where every test was skipped),
[`kind-mismatch.md`](examples/plain-node-project/reviews/kind-mismatch.md) and
[`count-mismatch.md`](examples/plain-node-project/reviews/count-mismatch.md).

Those rules read the claim's wording, which is deliberately narrow and only in
English. A claim can also say outright which numbers it rests on, as
predicates inside the tag:

```markdown
**Claim**: the suite runs 71 passing tests.
**Grounding**: VERIFIED[tests-a3f91c: exit=0, passed>=71, failed=0]
```

Every key is read off the cited block, so a predicate checks the same way on
any machine: `exit`, `stopped` (`none`, `timeout`, `overflow`, `killed`), and
the work-summary counts - `passed failed skipped todo` on a test run, `files
ignored errors warnings` on a lint run. Values are whole numbers; `stopped`
takes only `=` and `!=`. An unknown key, a fragment that does not parse, a key
given twice or a count the artifact does not carry is an error, never dropped,
and so is a `VERIFIED[...]` bracket that is not an address at all - it does not
fall back to bare `VERIFIED`. The skeleton writes the predicates for you, read
off the run it gathered. There is no duration key: how long a run took is not
a property of the code.

Every failing finding carries a `fix` where one is mechanical - printed under
it, as its own field in `--format json`, and in a GitHub annotation. A claim
over the wrong run, or with the wrong number, is offered the claim its run does
back; a receipt whose quote is wrong is offered the file's real first line:

```text
✘ the suite runs four passing tests, including the new string case. (review.md:17)
        VERIFIED[tests-333881] `passed>=4` does not hold - the artifact says passed=3
        fix: replace the claim and its grounding with the lines below - or mark the claim UNVERIFIED:
          **Claim**: The test suite ran 3 passing tests and reports no failures.
          **Grounding**: VERIFIED[tests-333881: exit=0, passed>=3, failed=0]
```

`npx evidence-layer claims review.md --fix` marks every claim an error failed
UNVERIFIED, in the file, and checks it again. It never rewrites a sentence or a
predicate to fit its run - that would make a claim pass by changing what it
says - so it is the one fix applied for the writer rather than offered.
[`fix-me.md`](examples/plain-node-project/reviews/fix-me.md) is a review to
try it on, a copy of it rather than the file itself.

For a review posted as a pull request comment, `generateClaimSkeleton` and
`generateSampleSkeleton` take `{ fold: true }`: each artifact block, and the
Sample integrity table, goes in a `<details>` fold, and the Claim and Grounding
lines stay outside it. A fold's summary names the command without its paths -
`summaryCommand` drops them - because a path outside a fence reads as a
citation.

Two different blocks under one id are an error too: an id is an address, and an
address names one thing.

The counts come from the project's own test report, read after the step has
finished and appended by the gatherer - never by the tool, which is why only
the last line counts. `evidence-layer/adapters/test-reports` reads the shapes a
run leaves: JUnit XML, which pytest, Maven and Gradle, `dotnet test`,
`go-junit-report` and `jest-junit` all write; pytest's closing line; vitest's
`Tests` line; and `node --test`'s totals. Every reader is pinned by output
recorded from a real run. The gather's commands are the project's too
(`testCommand`, `typecheckCommand`, `lintCommand`), so a project that is not on
pnpm gathers the same way. A Python project, say:

```js
import { gatherEvidence } from 'evidence-layer'
import { summariseJUnit } from 'evidence-layer/adapters/test-reports'

await gatherEvidence({
  repo: '.',
  base: 'origin/main',
  skip: ['lint', 'lockfile'],
  plan: {
    typecheckCommand: () => 'mypy .',
    testCommand: () => 'pytest -q --junitxml=reports/junit.xml',
  },
  summaries: { test: summariseJUnit('reports/junit.xml') },
})
```

JUnit cases are counted from the `<testcase>` elements, not from a suite's own
`tests=` attribute. A report older than the step - left behind by an earlier
run - is refused rather than read, and a step with no usable summary says why
in the bundle instead of going without one silently. Write the report where
git does not look (`reports/` in `.gitignore`), or the gather will say,
correctly, that the tree changed while it ran. A directory of reports, as
Surefire writes, is summed.

`runAsync` is the runner for those steps. A timeout kills the whole process
tree - a process group on POSIX, `taskkill /T` on Windows - rather than only
the direct child, and it reports within a grace period even when some process
in the tree will not release the output. Give it the arguments as an array -
`runAsync('pnpm', { args: ['vitest', 'run', changedFile] })` - whenever one of
them is not a literal you wrote, such as a changed file's path: on POSIX no
shell reads them, on Windows each is quoted for cmd.exe (one containing `"` or
`%` is refused, not run as something else), and the recorded command line is
the same on both, so the artifact id is too.

## The seal: was this block gathered, and is it still about this code?

`claims` proves a tag points at a block in the document. On its own it cannot
tell a block the gatherer wrote from one typed in by hand, or a review written
right after the tests ran from one written after three more edits - which is
what an agent does by default: it edits the code after running the suite, then
reports the suite.

So every `gatherEvidence()` also publishes a **sealed run** into the checkout's
git directory (`git rev-parse --git-path evidence-layer`, never the source
tree): the bundle it wrote, a hash of every artifact block in it, and a
fingerprint of the source it ran against - a git tree id of the working
directory's *content*, computed through a throwaway index so the real one is
never touched. A gather whose own steps wrote into the files they were checking
(a formatter, a code generator, a test that leaves a file behind) is not sealed,
and the bundle names the step and the path.

```bash
npx evidence-layer claims review.md --seal
```

adds two checks. Every cited block must be one the current run produced,
unedited. And the code must still be what that run was gathered from: editing a
file after gathering is an error naming the file, while committing content that
did not change is not, and neither is writing the review itself. A pass says
exactly what it covers - tracked and non-ignored files, not ignored ones,
dependencies or the environment - and an untracked file too large to hash makes
it `unverifiable`, never a pass.

The seal is not an attestation. It lives where the same agent can write, so it
catches the default failure, not someone rewriting it on purpose; CI, which
gathers its own evidence, stays the independent party. Without `--seal`,
nothing changes and nothing local is read.

It also holds only in the checkout that gathered. Where the review is written
somewhere else - a later CI job, a person reading the bundle CI uploaded -
`--bundle <file>` does the provenance half instead: every cited block must be,
canonically, the one that bundle carries under its id (`bundle/edited`,
`bundle/not-gathered`). A bundle has no fingerprint of the source, so freshness
is not checked; give `--sha` the commit under review, and a bundle from any
other commit fails as `claims/wrong-commit`. A bundle that is not there is bad
usage, never a pass.

## In an agent's session: the runtime gate

CI checks a review after a person can already read it. The gate runs the same
checks at the moment the agent says it is done, so an unbacked "tests pass" is
caught by the agent that wrote it:

- **When the session starts**, it shows the agent the claim grammar as a
  filled-in example rather than a template of placeholders, lists the claims
  the sealed run for this commit backs, ready to paste, and records which
  review files exist, so that it later checks only what *this* session wrote.
- **Before each file write**, it refuses a write into its own ledger - an
  accidental-write guard, not a sandbox: a shell command can still write there.
- **When the agent stops**, it runs `claims`, `receipt` and, against the sealed
  run, provenance and freshness - over every review file the session changed
  (default `review.md`) and the `**Claim**:` lines of the agent's final reply,
  whose ids resolve against the sealed bundle. Ordinary prose is not graded. An
  error blocks the stop, and the agent fixes its claims from the reason: one
  numbered item per failing claim with its problem and its fix, the `--fix`
  command for a review file, and the claims the current run does back.

Two budgets keep it from becoming a trap. A **retry episode** opens at the first
stop with errors and closes at the first clean one; inside it the gate blocks
at most twice, then lets the agent through with the errors attached, once -
later stops over the same review, run and code say nothing. Editing text does
not reset it; a clean check closes it, and so does a stop with nothing left to
check, which is journalled as closed without one. And the gate **fails open**:
if it cannot run, the session continues and is told why. `--keep-blocking`,
`--fail-closed` and `--strict` (both, and `unverifiable` blocks too) are the
stricter trades. Every decision - including each allow that checked nothing,
which is never recorded as a pass - goes into a journal in the checkout's git
directory, not the committed one; `npx evidence-layer journal report
--include-gate` counts blocks, clean stops and stops let through without a
clean check, and lists the blocks nobody has tagged yet, by id, so `journal
tag <id> real|false --gate` marks one without reading the journal. The id is
never in the reason the agent reads: the blocked party does not grade its own
blocks.

Where the gate tells the agent to gather, it names the command: the project's
`evidenceLayer.gather` in package.json when set, otherwise the one the current
run recorded, otherwise `<package manager> run evidence` when there is an
`evidence` script - with the base the current run was gathered against.

With the package installed in the project:

```bash
npx evidence-layer init claude            # or --local for .claude/settings.local.json
```

writes the three hooks into `.claude/settings.json`, keeps every hook that is
not its own, and replaces its own in place when run again. Or install the
Claude Code plugin from this repository, which finds the package the project
installed and says the gate is inactive when there is none:

```text
/plugin marketplace add AndrewBogdanovTSS/evidence-layer
/plugin install evidence-layer@evidence-layer
```

For Codex:

```bash
npx evidence-layer init codex             # writes .codex/hooks.json
```

merges the same three hooks into `.codex/hooks.json` the same way. Codex runs a
project's hooks only once they are trusted, so approve them in `/hooks` - and
again after `init` runs with different flags, since a changed command is a new
hook to Codex. Codex gives a hook no project-directory variable, so the command
finds the package from `git rev-parse --show-toplevel`, as Codex's
documentation does; on Windows, where hooks run under `cmd.exe`, it uses
`npx --no-install` instead. Codex edits files with `apply_patch`, so the
pre-write guard reads every path the patch adds, updates, deletes or moves a
file to.

`npx evidence-layer hook claude|codex <event>` is what all of these run. It
reads the hook's input on stdin and answers in the host's own protocol - always
with exit 0, because both hosts read an exit code as a decision, and this
package's `2` (bad usage) is their "block".

## In CI: the GitHub Action

```yaml
- uses: actions/checkout@v5
- uses: AndrewBogdanovTSS/evidence-layer@v0.17.0
  with:
    claims: review.md            # comma- or newline-separated
    # receipt: review.md         # needs fetch-depth: 0 and the target branch
    # governance: 'true'         # also run governance --enforce
    # strict: 'true'             # warnings and unverifiable fail too
    # bundle: evidence.local.md  # hold every cited block to the bundle CI gathered
    # sha: ${{ github.event.pull_request.head.sha }}
```

Every finding that is not a pass becomes an annotation on its line, titled by
its [code](docs/evidence-layer.md#machine-readable-output), and the job
summary lists them. The action runs the evidence-layer the project installed,
so CI and a laptop give the same verdict; with none installed, it fetches the
exact version the action was released with - never `latest`. The ref above is
the current release: `pnpm release` rewrites it, and `check:docs` fails when it
names any other. Its outputs are
`exit-code` and `conclusion` (`success`, `failure`, `flaky`, `misconfigured`),
and a step with nothing to check, a missing review or an unusable package is
`misconfigured`, never a pass.

For the evidence to be CI's rather than the author's, gather in CI. The
gather exits 1 when a step failed, bundle written regardless, so it can be the
job's test run rather than a second one; upload the bundle, and the review -
written by a model in a later job, or by a person reading the uploaded bundle -
is held to it with `bundle:`, which runs `claims --bundle`. Without that, a
check in another job proves only that each tag names a block in the review
itself, which a block typed by hand under an invented id satisfies; `--seal`
proves more, but only in the checkout that gathered.
[`examples/plain-node-project/.github/workflows/ci.yml`](examples/plain-node-project/.github/workflows/ci.yml)
is the layout: gather, then review, then verify
([DEC-0011](docs/decisions/0011-ci-evidence-crosses-jobs-as-a-bundle.md)).
Its `npm run ci:local` runs those jobs on your machine the same way, the model
step read out of the workflow rather than copied, so you see what CI will
report before you push - see
[the example's README](examples/plain-node-project/README.md#before-you-push-npm-run-cilocal).

Outside the action, `--format github` on `claims`, `receipt` and `governance`
does the same in any `run:` step. A review is text written by someone this
package does not trust, so it is never handed to the runner as a command: the
annotations are escaped as the runner reads them, and the report that quotes
the review runs under `::stop-commands::` with a token chosen per run
([DEC-0007](docs/decisions/0007-github-action.md)).

## In CI: Azure Pipelines

There is no task to install: a script step runs the evidence-layer the project
installed, with `--format azure`.

```yaml
- script: pnpm exec evidence-layer claims review.md --bundle evidence.local.md --sha $(System.PullRequest.SourceCommitId) --format azure
  displayName: The review, held to the bundle
```

Every finding that is not a pass becomes a `task.logissue` on the step - an
error, or a warning whose message opens with `unverifiable` or `flaky` - with
its file, line and [code](docs/evidence-layer.md#machine-readable-output), and
on an agent the summary is attached to the run with `task.uploadsummary`. The
exit code is the text mode's, and the step's result follows from it.

The agent obeys a `##vso[` anywhere in a line, not only at its start, and has
nothing like `::stop-commands::`, so under `--format azure` every piece of
review text the package prints - the report, the issues, `governance`'s JSON
block - is defanged: a zero-width space between the two `#`s, which a reader
does not see and the agent does not match, and `#` inside the JSON block,
which parses back to the same text
([DEC-0012](docs/decisions/0012-azure-pipelines-output.md)). `--format text`
and `--format json` print the review as written: in an Azure step, use
`azure`.

## Supported hosts

| Host | Adapter | Protocol checked against |
| --- | --- | --- |
| Claude Code | `src/hosts/claude-code.ts` | code.claude.com/docs/en/hooks, read 2026-10-17 |
| Codex | `src/hosts/codex.ts` | developers.openai.com/codex/hooks and `codex-rs/hooks/schema/generated` at openai/codex 8c07694, read 2026-10-18 |

A host is listed here only with an adapter and recorded inputs it is tested
against (`test/fixtures/hosts/`), and `check:docs` holds the table to that. The
inputs are written from the documented schema, not captured from a live
session, so they show the adapter keeps to the protocol as documented - not
that a later release of the host still speaks it. Other hosts follow once their
hook protocol is documented well enough to write fixtures against.

## Exit codes are a contract

| code | meaning |
| --- | --- |
| 0 | clean |
| 1 | at least one error |
| 2 | bad usage - never a pass |
| 3 | flaky - non-zero, but not the same claim as "the change broke something" |

Five outcomes, not two: `pass`, `warning`, `error`, `unverifiable`, `flaky`.
`unverifiable` is deliberately neither a pass nor an error. A checker that
reports success when it could not run manufactures confidence out of nothing.

Findings print one status icon per level, coloured unless `NO_COLOR` is set to a
non-empty value - [no-color.org](https://no-color.org)'s exact rule, so an
inherited opt-out can still be cancelled with `NO_COLOR=`. Colour is not gated
on `isTTY`: sandboxed sessions and CI log viewers have no terminal attached and
render ANSI perfectly well.

For a program rather than a person, `claims`, `receipt` and `governance` take
`--format json`: stdout is one JSON report and nothing else, and the exit code
is the same. `--format github` is the text plus one annotation per finding and
a job summary, for a GitHub Actions step; `--format azure` is the text plus one
logged issue per finding and a run summary, for an Azure Pipelines step. Each finding carries a `code` - `claims/predicate-unmet`,
`receipt/wrong-base`, `seal/stale` - naming the rule that produced it. The
sentences will be reworded; a released code keeps its meaning. Every code is
listed in [`docs/evidence-layer.md`](docs/evidence-layer.md#machine-readable-output).

## What "zero-config" means, precisely

`claims`, `receipt`, `ci-summary`, `journal`, governance, exceptions and misses
need **no configuration at all** - they operate on markdown text, git output and
`package.json`, which every project already has. Call `gatherEvidence({ repo,
base })` with nothing else and it plans `pnpm lint`, `pnpm typecheck`, a
lockfile check and `pnpm test` - the three scripts an ordinary Node project
already has names for, plus one fact `pnpm-lock.yaml` can answer about itself -
and reports the working tree's own status alongside them. Any of those
commands can be the project's own instead, and the work-summary counts need a
summariser, because which report a project writes is that project's business.

What was **never** claimed to be zero-config, because it cannot be: any check
that asserts a fact specific to one project - a route existing, a dependency
pinned to an exact version, a build fitting a size budget. Those are facts about
that project, not about Node, and belong in that project's own script. This
repository's `scripts/check-docs.ts` and `scripts/check-deps.ts` are the worked
examples: one checks the claims *this* README makes, the other checks that
every dependency *this package* declares is actually used, and both live here
rather than in the package because nobody else's README or manifest makes
those exact claims.

## Using it as a library

```js
import { lintClaims, checkReceipt, parseReceipt, gatherEvidence, CODES } from 'evidence-layer'
import { parseTestCount } from 'evidence-layer/adapters/node-default'
import { summariseJUnit } from 'evidence-layer/adapters/test-reports'
```

Everything the CLI does is exported. `src/core/` has no knowledge of any
project's stack. The adapters are the files allowed to know one:
`src/adapters/node-default.ts` knows it is running on Node and how a handful of
common test reporters print their totals, and `src/adapters/test-reports.ts`
knows the JUnit XML, pytest, vitest and `node --test` formats a test step's
work summary is read from.

## The portability test

A claim that a package works on "any project" is exactly the kind of claim this
package's own `claims` check would tag UNVERIFIED if nobody had checked it.
[`examples/plain-node-project/`](examples/plain-node-project) is a deliberately
unrelated fixture - plain JavaScript, no TypeScript, no framework, no monorepo,
its own unconnected `package.json` - that
[`test/portability.test.ts`](test/portability.test.ts) exercises
`readInvariants`, `reachableCommands`, `lintClaims`, `checkReceipt` and
`renderSummary` against, and [`test/example.test.ts`](test/example.test.ts)
runs its whole loop on a standalone copy - gather with counts, a review of the
suggested claims passing `claims --seal` and, where there is no seal,
`claims --bundle`, the same review failing once the code changes, and the
gather failing when the suite does. Clone it, run the layer against it, and see
the checks fail on purpose: [`examples/plain-node-project/README.md`](examples/plain-node-project/README.md)
is the guided version, and the project is set up the way one using this
package should be - evidence script, a CI workflow that gathers before anyone
reviews, runtime-gate hooks.

Inside this checkout it is a template, not a repository: git answers from
evidence-layer's top level, so its hooks would check evidence-layer's
`review.md` and its seal would fingerprint the whole checkout.
`npm run standalone` in it copies it out as a repository of its own, with this
checkout linked in - the copy `test/example.test.ts` runs on.

## The boundary is a test, not an intention

Nothing under `src/core/` may import anything but Node builtins and its own
siblings, and `src/hosts/` - one file per agent host - only builtins, the core
and its own contract. That is checked by
[`test/boundary.test.ts`](test/boundary.test.ts) on every run, because a layer
separation enforced by good intentions is worth nothing. Node builtins are fine there: this is CLI tooling, expected to shell
out and touch the filesystem, not a sandboxed engine.

## What this repository checks about itself

The package is its own first consumer. `pnpm check:all` runs this repository's
own checks and then checks that something actually runs them - an invariant no
git hook or CI workflow reaches is a finding, because a rule with no trigger is
decoration.

The suite is **576 tests** across **42 files**, and that sentence is checked
too - `check:docs` runs the suite and compares. Change the number and watch it
fail; a check nobody has seen fail is indistinguishable from a check that
cannot fail.

```bash
pnpm evidence --base origin/master # gather this repository's own evidence bundle
pnpm check:docs     # do the claims on this page still hold?
pnpm check:deps     # is every dependency this package declares actually used?
pnpm check:ladder   # did this commit climb the decision ladder it says it did? (CI: every new commit)
pnpm check:all      # every check, plus: does anything run them?
pnpm ci:local       # CI's jobs on this machine, reported as CI would - what it cannot run is `unverifiable`
pnpm journal:report # what the checks have found here, over time
```

CI runs the suite on Node 22 and 24 and, in a separate job with no package
manager and no install, takes the `dist/` the build job produced and runs it on
bare `node` - 22.0.0, the oldest `engines` allows, as well as 22 and 24. If that
job passes, "zero runtime dependencies" is a checked fact for everything the
smoke script loads, rather than a sentence on this page. Two more jobs run the
example project's CI handoff, which GitHub would not run from inside this
repository: one gathers in a standalone copy and uploads the bundle, the other
downloads it and holds a review to it with the action's `bundle:` input.

## What this does not do

- It does not make findings correct. Access, gathered evidence and grounded
  claims are necessary, not sufficient. None of the three makes a claim true.
- It does not stop someone determined to fake it. It removes the *default*
  failure, which is the one that actually happens.
- It does not judge taste. "This will be hard to maintain" is a legitimate
  review comment and always will be, untagged - prose outside a `**Claim**:`
  line is never graded. It just must not be dressed as a check.
- The reachability scan reads literal command strings, so a command assembled at
  runtime is invisible to it unless the invariant self-discloses that fact and
  accepts `unverifiable` instead of a guess. Blind spots that are written down
  can be calibrated against; blind spots that are not, cannot.
- The misses journal measures a floor, not a rate. A miss nobody traced back to
  the review that let it through stays invisible, so it supports a trend and a
  case-by-case reading, never a claimed percentage of defects caught.

## Releasing

```bash
pnpm release              # patch: 0.1.0 -> 0.1.1
pnpm release minor        # 0.1.0 -> 0.2.0
pnpm release 1.0.0        # exactly that
pnpm release --dry-run    # run every check, print the plan, change nothing
```

One command: it checks, bumps, commits, tags and pushes. The tag is what
triggers publication - nothing is published from a laptop, because npm only
generates a provenance attestation inside CI, and a local publish would quietly
ship a version weaker than every other version. The workflow publishes through
npm's Trusted Publisher: its own OIDC token is the only credential, so there is
no long-lived npm token to leak, and a broken trust setup fails the publish
instead of falling back to one.

Before it touches anything it checks that the release is cut from the default
branch, that the tree is clean, that the commit is the one the remote has, that
the tag is free, that the version has never been published, and that
`pnpm check:all --enforce` passes. Every one of those exists because it went
wrong during the first release of this package.
