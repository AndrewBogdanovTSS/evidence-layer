# Roadmap, 17 November 2026 to mid-January 2027

What to build in the next two months, and in what order. It follows
[the review of 0.18.0 and its roadmap](review-and-roadmap-2026-11.md), which
was last revised on 2026-11-14, and does not replace it: the findings there
(A1 to D6) and the item numbers (1.5b, 1.10, 1.11, 2.1 to 2.8) are used here
as written. What this document adds is what was measured on 2026-11-16, the
dates that fall inside the window, and an order with a release for each
step.

## Where things stand

1.5b (waits on counts), 1.11 (waits on a date) and the half of 1.10 that
holds a review to CI's bundle.
[Pull request 17](https://github.com/AndrewBogdanovTSS/evidence-layer/pull/17)
is open: a `DOCUMENTED` claim's cited file must exist. Its twelve CI checks
completed with success.

What is new since 2026-11-14:

1. **The suite turns red on 2026-12-06.** The dated test in
   `test/claims.test.ts` ("is still ahead - bare VERIFIED is a warning only
   until 2026-12-06") fails from that day until item 1.11 lands. It was
   written to do exactly that. It is twenty days out, and from then every
   pull request and every release is blocked on it.

2. **The suite does not pass reliably on the maintainer's machine.** Three
   full runs on Windows on 2026-11-16 all failed, each on timeouts and not on
   the same tests: one through `check:all` (`pnpm test` exited 1), one with a
   single failure, one with three (`tests-643938@15f9356`: 670 passed, 3
   failed, 6 skipped). The single failure was the `ci:local` end-to-end case
   in `test/example.test.ts`, at 32.8 s against an explicit budget of 30 s;
   among the three was a `restamp` case that hit 60 s. `test/example.test.ts`
   run alone passes, in 65 s. `vitest.config.ts` gives Windows a default of
   60 s, and an explicit `30_000` on a test overrides it - there are nine, in
   `test/example.test.ts` and `test/gate.test.ts`. Every CI job is
   `ubuntu-latest` and green, so nothing a pull request triggers sees any of
   this, and `pnpm check:all --enforce` - the step AGENTS.md asks for before
   a push - exits 1 here. This is finding D2 with a cost attached: the honest
   path fails on the machine the package is written on. The machine was not
   otherwise idle, so the counts are what was observed, not a rate.

3. **DEC-0014 has a deadline and almost no data.** It must be decided by
   2026-12-31. Its threshold for blocking by default is thirty stops
   journalled as `unclaimed-result` and tagged by hand, at most three of them
   false. The gate's journal in this checkout: 10 of 24 stops checked
   something, 2 reported a result outside any claim, and neither is tagged.

4. **The prose rule has a known cause of false positives.**
   [Issue 18](https://github.com/AndrewBogdanovTSS/evidence-layer/issues/18):
   `unclaimedResults` reads the words inside an inline code span, so a
   sentence that only cites `tests/clean.test.ts` warns. In a corpus of 19
   reviews that was 5 of 40 warnings. Tags collected before this is fixed
   measure the bug.

5. **Nothing to decide DEC-0010's C1 from.** Its threshold is more than 1 in
   10 blocks landing on a review the turn did not touch. The journal has no
   blocked stop at all.

6. **No sign of use outside the maintainer's own projects.** Seven stars, no
   forks, and the one issue was filed by the maintainer. Downloads sit
   between 1 and 40 a day, with spikes on the days a release was published
   (521 on 2026-10-18, 344 on 2026-11-15), which is what mirrors and scanners
   look like. The earlier roadmap said it had no evidence about users and
   that, if adoption is the binding constraint, item 2.2 belongs ahead of
   most of Phase 1. This is the evidence, as far as it goes.

7. **The one real consumer keeps its own layer over the package.**
   [The Azure DevOps plan](azure-devops-integration.md), section 1.5: a
   scoped gather (lint, a typecheck matrix, the tests near the change), a
   review verifier with its own rules, and a governance check with its own
   trigger graph. Each of those is something the package does not yet let a
   project say, and so wrote for itself.

8. **The journal's findings are still empty.** `journal.jsonl` holds one
   miss, untagged. No check's findings are journalled from CI (finding C2,
   and what is left of item 1.10).

9. **Small debts.** `check:deps` warns that the exemption for
   `@arethetypeswrong/core` no longer applies. The host protocols were read
   on 2026-10-17 and 2026-10-18 and nothing brings those dates back up
   (finding C5). The package's exports are 159 on `master` - 148 from the
   main entry, 11 from the two adapters - and 160 with pull request 17.

## The order, and why

Three things decide it.

**Dates first.** 2026-12-06 and 2026-12-31 are in the repository's own code
and frontmatter. Work that does not respect them gets interrupted by them.

**Then the cost of adopting.** The earlier roadmap's measure - of the stops
the gate saw, how many checked something - is a number per checkout, and
there is one checkout. More rules will not move it; more places running the
gate will. Facts 6 and 7 say the same thing from two sides: nobody outside
has adopted the package, and the one project that has needed to write around
it. So `evidence-layer gather` (2.2) with custom steps (2.1) comes before
everything in Phase 2 and Phase 3 that widens what can be claimed.

**Then the loop in this repository.** A review held to CI's bundle here is
what fills the journal, and the journal is the only thing a case study can
be written from.

A release every two weeks, four in the window. The twenty minor releases of
the last two months were the right pace for finding the shape; a consumer
that pins an exact version reads every one of them.

### 0.22.0, on 2026-12-06 to 2026-12-08 - removal ⚠

Items 1.11 and 2.8, together.

- Bare `VERIFIED` becomes an error. The proximity mode behind it is deleted:
  `ARTIFACT_WINDOW`, positional consumption, the id-less `artifact` fence.
- `SkeletonArtifact.timedOut` and the colon-named command aliases are
  removed.
- The pull request is ready before 2026-12-06 and merged on the day, so the
  dated test is red for hours, not days.
- Before the release, the consumer's review corpus is run for
  `claims/bare-verified`. If it has any, they are restamped first.

Done when the dated test is replaced by one expecting the error, and
`test/fixtures/exports.json` is shorter than it was.

### 0.23.0, by 2026-12-21 - gathering without a script

Item 2.2, with as much of 2.1 as it needs.

- A decision record first. The configuration is a thing a project builds on,
  so its shape is a compatibility promise from the day it ships.
- `evidence-layer gather`, driven by an `evidenceLayer` block: steps as
  `{ name, kind, command }`, report readers by name. `init` scaffolds it.
- A custom step is sealed as the built-in four are, and a claim cites it
  with a predicate.
- Not in this release: work summaries for more kinds (typecheck error
  counts, coverage). They are the rest of 2.1 and can follow.

Done when a Python fixture gathers with no `.mjs` file, a build step's block
is sealed and cited, and this repository's own `pnpm evidence` runs from the
configuration - so that `scripts/gather-evidence.ts` is something removed,
not something added to.

It is also the test of fact 7: if the consumer's scoped gather cannot be
written as this configuration, the configuration is wrong.

### By 2026-12-31 - decide DEC-0014

This document recommends accepting **O4** on the date: a result stated as
prose blocks a stop only under `--strict`. It needs no data - whoever passes
`--strict` asked for the stricter trade - and it gives the record invariants
and a `review_by`, which is what `decide_by` is for.

**O3**, blocking once by default, stays behind the threshold the record
already states. At two unclaimed stops in twenty-four, from one checkout,
thirty tagged by 2026-12-31 is unlikely; deciding O3 on fewer would be
choosing the threshold when the numbers are in, which the record was written
to prevent.

It depends on issue 18's fix being released, in 0.21.0.

The decision is the maintainer's.

### 0.24.0, by 2027-01-17 - a review held in CI, here

What is left of item 1.10.

- A decision record: how CI holds an author's review to CI's own bundle. Two
  problems stand in the way, and they are different. A review that is part
  of a commit cannot name that commit - a review in the pull request's
  description avoids it. And CI's ids are not the author's, since an id
  hashes output and test output carries timings - DEC-0010's C5 does not
  answer that either, because relabelling a run for a new commit keeps the
  author's ids. This document's recommendation, for the record to weigh:
  match by step, as `restamp` already does, and hold each claim's predicates
  to CI's run of the same step.
- What `claims`, `receipt` and `governance` find in CI is journalled, so
  `journal:report` has findings to show (C2).
- The host protocols get a `review_by` that `check:docs` holds, and fixtures
  recorded from a live session (2.7). By mid-January the documentation will
  have been read three months ago.

Done when a fixture pull request carrying a claim CI's run does not back
fails here, and `journal:report` on `master` lists findings.

### If there is time left

- An invariant names its test, and governance holds it to the suite's report
  (2.3). Most invariants in the repository still say "enforced by `pnpm
  test`", so deleting the test behind one leaves the report green.
- A published JSON Schema for the report, with golden fixtures.

### Not in this window

- **A protocol, attestations, an adapter SDK** - the development strategy's
  first quarter. Nothing outside this repository reads the format yet;
  freezing it now would standardise it before anyone has pushed back on it.
- **DEC-0010's C1 and C5.** C1 has no data (fact 5). C5 is not what stands
  between a review and CI (above).
- **New hosts and new output formats.**
- **Blocking on prose by default** (1.5b as O3).
- **Items 2.4 and 2.5**, quotes in citations and wider path patterns, unless
  the consumer's corpus shows them costing something.
