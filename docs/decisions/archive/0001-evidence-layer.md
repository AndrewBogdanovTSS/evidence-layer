# DEC-0001: Claims about this repository are checked, not trusted

## Context

This repository already enforced the thing it cared most about. The three-layer
architecture is not a convention here - `eslint.config.js` makes a `vue` or
`three` import inside the engine a build error, and the file says so in its
header: *"the three-layer architecture is worth nothing if it is enforced by
good intentions."*

Everything else was on trust. The README asserted a test count, a build size, a
fixture's shape and a set of pinned versions. All four were true when written.
None of them had a clock. And a review of a change here - written by a person or
generated by a model - could assert anything at all about what it had read and
what it had run, in a register that reads identically whether or not any of it
happened.

That asymmetry is the whole subject. Confident prose is not evidence of anything,
and the fix is not to ask for more care. It is to make the claims checkable and
then check them.

## Decision

Five commands, each making one class of claim falsifiable, and one that checks
whether anything runs them:

| Command | Makes falsifiable |
|---|---|
| `pnpm check:docs` | every number in the README |
| `pnpm fingerprint` | "the refactor is behaviour-preserving" |
| `pnpm evidence` | "I checked that" - by gathering the proof before the review is written |
| `pnpm check:claims` | the grounding tags in a review |
| `pnpm check:receipt` | "I read the code" |
| `pnpm check:all` | "this is enforced" |
| `pnpm ci:summary` | "the checks ran" |

Constraints that shaped them:

- **No new dependencies.** `tsx` and `vitest` were already in the workspace.
  Governance tooling that needs its own runtime does not survive its first
  dependency review, and this repository has to stay a game rather than become a
  framework for checking games.
- **One file, one idea, small enough to read in a sitting.** Five short scripts
  over one flag-driven tool, even though that means a little duplication. These
  files are meant to be read and copied.
- **Three outcomes, never two.** Pass, fail, and `unverifiable`. A checker that
  reports success when it could not run manufactures confidence out of nothing.
- **Warn-only first.** Everything lands reporting but not failing. Enforcement is
  one flag, flipped when the report has been clean for a while, by a person who
  is named before it matters.

## Consequences

- A README number that goes stale now fails a check instead of quietly misleading
  a reader.
- A review may still be wrong. Access, gathered evidence and grounded claims are
  necessary, not sufficient - none of the three makes a finding correct, and none
  of them judges taste.
- The rules above are only real while something runs them, which is why the last
  row of that table exists and why every invariant in this file's front matter
  names the command that enforces it. `pnpm check:all` resolves those names
  against the trigger graph, so an invariant that claims enforcement it does not
  have fails this record's own check.
