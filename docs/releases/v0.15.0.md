## evidence-layer 0.15.0

A writer that gets a citation wrong is told the correction, not left to work
it out - the mistake a smaller model makes most, and the one it fixes worst
from a sentence. Nothing here changes what an exit code means.

### Claims

- **Two new rules read a claim's words against the block it cites.**
  `claims/kind-mismatch`: a claim that names a kind of run - tests, lint,
  typecheck, lockfile, audit - must cite a run of a kind it names; "Lint
  reports no violations" over a typecheck block is an error, whatever the
  typecheck showed. `claims/count-mismatch`: a count the claim states about
  the run ("72 passing tests", "ran 71 tests", "7 files were linted", "0
  failures") must be the count the run's work summary carries. A number no
  word ties to the run ("adds 3 tests") is not read, nor is a sentence about
  what used to be true ("fixes the 2 failing tests"), nor the number a count
  is taken out of ("3 of 71 tests failed"). Both are deterministic
  and narrow, in English, like the outcome rules; a claim that names no kind
  or no count is held to nothing. A count spelled out, zero to twenty, is read
  as the same number - "four passing tests" over `passed=3` fails like "4
  passing tests" does. A number straight after a hyphen is not read, so
  "twenty-one tests failed" is not a count of one.
- **Failing findings carry a `fix`.** Where one is mechanical: the claim the
  cited run does back, as the skeleton writes it, with its predicates; the
  grounding line with the run's own predicates for a malformed or unparseable
  tag; the one run of the right kind for an id that does not resolve; the
  file's real first line for a receipt quote that is wrong; the merge-base for
  a wrong base. Printed under the finding, a field in `--format json`
  (report schema 5) and part of a GitHub annotation.
- **`claims review.md --fix`** marks every claim an error failed UNVERIFIED,
  in the file, then checks it again. It never rewrites a sentence or a
  predicate to fit its run.
- `lintClaims` takes `suggestFrom`: a document - the sealed bundle - whose
  runs a fix may offer without them resolving a claim.

### The runtime gate

- **Session start shows the grammar as a filled-in example**, not a template
  of placeholders, and lists the claims the sealed run for this commit backs,
  ready to paste.
- **A block reason is a numbered list**, one item per failing claim, each
  with its problem and fix; then the `--fix` command for a failing review
  file, in the project's own package manager; then the current run's ready
  claims, unless the code changed since it was gathered - checked there even
  when nothing in the report cited the run. A finding whose fix is to gather
  again names the project's gather command. Non-blocking findings follow,
  one line each; at most ten items are listed. The ready claims at session
  start say they hold only while no file has changed since the run.

### Fixes

- **The skeleton wrote one claim twice** when two steps ran the same command
  at the same commit - as in this repository, where the lint step is the
  typechecker. It now writes one claim per id.
- **`parseTestCount` read vitest's summary only when every test passed.** A
  run with a skipped or failing test (`516 passed | 3 skipped (519)`) gave
  `null`, so `check:docs` reported the README's test count as unverifiable in
  CI, where two Windows-only tests are skipped. It reads the total now, and
  mocha's total counts failing and pending tests too.
- **`claims --seal` could call changed code fresh.** An edit that kept a
  file's size, made in the second git last wrote the index - a commit, or the
  gather's own `git status` - left every file attribute unchanged to a git
  that compares timestamps to the second, as Linux's does. git rereads such a
  file only while its entry is not older than the index, and the
  fingerprint's throwaway copy of the index was dated the moment it was
  copied: when that fell in the next second, the edit read as no change -
  `seal/fresh` where `seal/stale` was due. The copy now keeps the index's own
  timestamp. The gate's freshness check uses the same fingerprint, so it had
  the same gap. Seen as an intermittent failure of the example's end-to-end
  test on Linux CI.

### Behaviour changes to check when upgrading

- **A review that passed may now fail** `claims/kind-mismatch` or
  `claims/count-mismatch`. Each comes with its fix, and `--fix` marks it
  UNVERIFIED.
- **`--format json` reports schema 5.** The only change is the optional `fix`
  field; a reader that checks `schema === 4` needs updating.

### Repository

- The suite is one size on every platform: a POSIX-only test is skipped on
  Windows instead of left out, and three tests that built Windows paths with
  `split('/')` or compared git's forward-slash output to a native path now
  pass there. On Windows the test timeout is 60 seconds, since starting a
  process there costs several times what it does on Linux.
- Four new example reviews fail on purpose, over real runs of the example
  project's suite: `kind-mismatch.md`, `count-mismatch.md`,
  `outcome-mismatch.md` (a failing run, a timed-out one, one where every test
  was skipped) and `fix-me.md`, a review to try `--fix` on. `check:all` holds
  each to its exit code and `test/codes.test.ts` to the codes it is named for;
  the example project's README walks through them.
- `check:all` runs the suite once. It used to run it twice - once for the
  README's test count, once as the suite check - and now hands the one run's
  output to `check:docs --suite-output <file>`. `pnpm check:docs` on its own
  still runs the suite itself.
- The suite is 533 tests across 39 files.
